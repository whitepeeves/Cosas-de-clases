¿Qué problema resuelve un entorno virtual?

Sin entornos virtuales, todas las librerías se instalan en el mismo sitio: el Python del sistema. Si un proyecto necesita django 3 y otro django 5, chocan. Además, instalar paquetes a mano en el Python del sistema puede romper herramientas que dependen de él y suele pedir permisos de administrador.

Un entorno virtual da a cada proyecto su propio espacio de librerías, independiente de los demás y del sistema. También permite reproducir el proyecto en otra máquina: con pip freeze > requirements.txt se guarda la lista exacta de dependencias y se reinstala con pip install -r requirements.txt.

¿Qué crea realmente python -m venv .venv?

Crea una carpeta llamada .venv con esta estructura:

  • pyvenv.cfg: un archivo de texto que indica dónde está el Python base con el que se creó (home = ...) y si el entorno ve o no las librerías del sistema.
  • bin/ (en Windows, Scripts\): contiene python (un enlace simbólico o copia del intérprete base), pip y los scripts de activación.
  • lib/pythonX.Y/site-packages/ (en Windows, Lib\site-packages): la carpeta donde se instalarán las librerías. Al principio solo trae pip.

No copia la biblioteca estándar de Python: el entorno sigue usando la del Python base. Por eso es muy ligero (unos pocos MB).

¿Dónde se guardan las librerías que instalamos dentro de él?

En .venv/lib/pythonX.Y/site-packages/ (en Windows, .venv\Lib\site-packages\). Cada entorno tiene la suya, así que lo instalado en un proyecto no afecta a los demás. Si se borra la carpeta .venv, desaparece todo y se puede recrear desde requirements.txt. Por eso la carpeta no se sube a Git (va en .gitignore) y sí se sube el requirements.txt.

¿Qué ocurre realmente cuando lo “activamos”?

Activar (source .venv/bin/activate, o .venv\Scripts\activate en Windows) ejecuta un script que solo modifica la terminal actual:

  • Añade .venv/bin al principio de la variable PATH, de modo que al escribir python o pip se ejecutan los del entorno y no los del sistema.
  • Define la variable VIRTUAL_ENV.
  • Cambia el prompt para mostrar (.venv).
  • Crea la función deactivate, que deshace todo lo anterior.

No instala nada ni cambia Python: es solo un atajo para que los comandos apunten al sitio correcto. Cuando el intérprete del entorno arranca, lee el pyvenv.cfg que tiene al lado y configura sus rutas para usar el site-packages del entorno.

¿Es obligatorio activarlo para utilizarlo?

No. Basta con llamar directamente al Python del entorno: 

.venv/bin/python script.py
.venv/bin/pip install requests

Funciona igual, porque ese intérprete detecta su pyvenv.cfg y usa su propio site-packages. Activar es solo una comodidad al trabajar en la terminal. En scripts, tareas programadas, CI o servidores se suele llamar directamente a la ruta del Python del entorno.

¿Qué diferencia hay entre un venv y una máquina virtual como VirtualBox?

Una máquina virtual emula un ordenador completo: tiene su propio sistema operativo y kernel, ocupa gigas y está muy aislada del equipo anfitrión. Un venv es solo una carpeta con un intérprete de Python enlazado y unas librerías: comparte el sistema operativo, los procesos, los archivos y la red con el resto del equipo.

Además, un venv solo aísla paquetes de Python. No aísla la versión de Python (usa la del Python base con el que se creó) ni las librerías del sistema que algunos paquetes necesitan. Para aislar eso hacen falta contenedores (como Docker) o máquinas virtuales.
